> На відміну від SQL де схема фіксована, в MongoDB ти сам вирішуєш як організувати дані. Ця свобода потребує свідомих рішень — неправильна схема на великих даних виправляється дуже болісно.

---

## Embedding vs Referencing

Головне рішення при проектуванні — зберігати пов'язані дані **в одному документі** чи в **окремих колекціях з посиланням**.

### Коли Embedding

```js
// все в одному документі
{
  _id: ObjectId("..."),
  title: "MongoDB Course",
  instructor: "Alice",
  lessons: [
    { title: "Intro", slides: "..." },
    { title: "CRUD", slides: "..." }
  ]
}
```

Embed коли:
- Дані зазвичай читаються разом
- Відношення "has-a" / "contains" (курс містить уроки)
- Дані оновлюються разом
- Дані архівуються разом
- Простіша модель важливіша за гнучкість

### Коли Referencing

```js
// courses колекція
{ _id: ObjectId("c1"), title: "MongoDB Course" }

// lessons колекція — окремо
{ _id: ObjectId("l1"), courseId: ObjectId("c1"), title: "Intro" }
{ _id: ObjectId("l2"), courseId: ObjectId("c1"), title: "CRUD" }
```

Reference коли:
- Висока кардинальність (один курс → тисячі уроків)
- Дані ростуть без меж
- Занадто багато дублювання
- Дані записуються в різний час
- Дочірня сутність може існувати без батьківської
- Розмір документа підходить до ліміту 16MB

## Duplicate Data — коли дублювання виправдане

Денормалізація (дублювання даних між колекціями) — **нормальна практика** в MongoDB якщо це прискорює читання і дані не змінюються часто.

| Тип | Опис | Приклад |
|---|---|---|
| **Immutable** | Ніколи не змінюється — ідеально для дублювання | Дата створення акаунту |
| **Temporal** | Важливо зберегти історичне значення | Адреса доставки на момент замовлення |
| **Sensitive to staleness** | Потребує частих оновлень | Кількість товару на складі |
| **Not sensitive to staleness** | Може бути трохи застарілим | Список рекомендованих товарів |

**Логіка вибору:**
- Дані immutable або temporal → дублюй сміливо
- Дані часто оновлюються → краще reference + `$lookup`
- Дані можуть бути трохи застарілими → дублюй + фоновий job для оновлення

## Atomicity

Write операція в MongoDB **атомарна на рівні одного документа**. Навіть якщо оновлення зачіпає вкладені документи — або все оновлюється, або нічого.

```js
// атомарна операція — один документ з вкладеними даними
db.orders.updateOne(
  { _id: orderId },
  { $set: { status: "shipped" }, $push: { history: { event: "shipped", date: new Date() } } }
)
```

Якщо потрібна атомарність між **кількома документами** → multi-document транзакції:

```js
const session = client.startSession()
session.withTransaction(async () => {
  await orders.updateOne({ _id: orderId }, { $set: { status: "paid" } }, { session })
  await inventory.updateOne({ _id: itemId }, { $inc: { qty: -1 } }, { session })
})
```

⚠️ Транзакції дорогі. Якщо часто потрібні транзакції — це сигнал що схема спроектована неправильно. Хороша схема мінімізує потребу в транзакціях.

## Інші практичні поради

### Індексуй те що часто запитуєш

Поля в `find()` фільтрах, `sort()`, `$lookup`, `$group` — кандидати на індекс. Детальніше: [[MongoDb - Indexes]].

Кожен індекс: мінімум 8KB простору + уповільнює запис. Моніторь використання індексів в проді.

### TTL для тимчасових даних

```js
// автовидалення сесій через 30 хвилин
db.sessions.createIndex({ updatedAt: 1 }, { expireAfterSeconds: 1800 })
```

### Маленькі документи — оптимізація

Якщо колекція складається з дуже маленьких документів:
- Встановлюй `_id` явно замість автогенерованого ObjectId (економить місце)
- Скорочуй назви полів (`last_name` → `lname`) — економить байти на кожному документі
- Embed маленькі документи один в одний

### Hardware constraint

Великі документи → більше RAM → читання з диска → деградація. Проектуй схему так щоб запити повертали тільки потрібні поля.

## Схемні патерни (Schema Design Patterns)

### Attribute Pattern — динамічні характеристики

**Проблема:** документи мають різні набори атрибутів (наприклад, технічні характеристики товарів: у телевізора є `screenSize`, у взутті — `shoeSize`). Якщо зберігати кожен атрибут окремим полем — неможливо ефективно індексувати.

**Рішення:** зберігати атрибути як масив пар `{ k, v }` і індексувати масив.

```js
// проблема: різні поля у різних документів
{ _id: 1, type: "tv",   screenSize: 55, resolution: "4K" }
{ _id: 2, type: "shoe", shoeSize: 42,   color: "black" }

// рішення: Attribute Pattern
{
  _id: 1,
  type: "tv",
  specs: [
    { k: "screenSize", v: 55 },
    { k: "resolution", v: "4K" }
  ]
}

// один індекс покриває пошук по будь-якому атрибуту
db.products.createIndex({ "specs.k": 1, "specs.v": 1 })
db.products.find({ specs: { $elemMatch: { k: "screenSize", v: { $gte: 50 } } } })
```

---

### Extended Reference Pattern — дублювання частини даних

**Проблема:** при referencing потрібен `$lookup` (дорогий JOIN) для кожного читання, хоча потрібні тільки кілька полів пов'язаної сутності.

**Рішення:** embed тільки ті поля які часто потрібні разом. Решту — читати через `$lookup` за потреби.

```js
// замість зберігання тільки userId...
{ _id: orderId, userId: "u1", amount: 120 }

// ...embed часто потрібні поля користувача
{
  _id: orderId,
  user: {
    _id: "u1",
    name: "Alice",      // потрібно в списку замовлень
    email: "a@a.com"    // потрібно для email-квитанції
    // НЕ embed: address, paymentMethods, preferences — рідко потрібні разом
  },
  amount: 120
}
```

**Коли підходить:** дані пов'язаної сутності **рідко змінюються** (ім'я, email) або зміна не критична (читання з невеликою затримкою прийнятне).

---

### Subset Pattern — зменшення розміру документа

**Проблема:** документ містить великий масив (наприклад, 1000 коментарів до товару), але при читанні потрібні тільки останні 10.

**Рішення:** зберігати в основній колекції тільки "популярну" підмножину, решту — в окремій колекції.

```js
// products — тільки 10 останніх відгуків
{
  _id: productId,
  name: "Laptop",
  recentReviews: [  // останні 10
    { user: "Alice", rating: 5, text: "..." },
    ...
  ]
}

// reviews — всі відгуки
{ _id: reviewId, productId: productId, user: "Alice", rating: 5, text: "...", date: ... }
```

```js
// при додаванні нового відгуку — атомарно
db.products.updateOne(
  { _id: productId },
  {
    $push: {
      recentReviews: {
        $each: [newReview],
        $sort: { date: -1 },
        $slice: 10  // залишити тільки 10 останніх
      }
    }
  }
)
```

### Bucket Pattern — групування time-series

**Проблема:** IoT або метрики генерують мільйони маленьких документів (один документ = один вимір). Колекція стає величезною, індекси роздуваються.

**Рішення:** групувати виміри в "відра" (buckets) по часу або кількості.

```js
// ❌ один документ = один вимір (проблема)
{ sensorId: "s1", ts: ISODate("2024-01-01T00:00:00"), temp: 22.5 }
{ sensorId: "s1", ts: ISODate("2024-01-01T00:01:00"), temp: 22.6 }
// ... ще 1440 документів на день

// ✅ один документ = одна година вимірів (Bucket Pattern)
{
  sensorId: "s1",
  hour: ISODate("2024-01-01T00:00:00"),
  count: 60,
  sum: 1353.0,
  min: 22.1, max: 23.0,
  readings: [
    { ts: ISODate("...T00:00:00"), temp: 22.5 },
    { ts: ISODate("...T00:01:00"), temp: 22.6 },
    // ... 60 вимірів
  ]
}
```

Переваги: менше документів → менший індекс → швидші aggregation по діапазонах часу.

> MongoDB 5.0+ має вбудований **Time Series Collection** який реалізує цей паттерн автоматично.

### Schema Versioning Pattern

**Проблема:** потрібно змінити схему документів без downtime і без одночасної міграції всіх даних.

**Рішення:** додати поле `schemaVersion` і обробляти різні версії в коді.

```js
// стара версія
{ _id: 1, name: "Alice Johnson" }

// нова версія після оновлення схеми
{ _id: 2, firstName: "Bob", lastName: "Smith", schemaVersion: 2 }
```

```js
// в коді — обробляти обидві версії
function getUserName(doc) {
  if (!doc.schemaVersion || doc.schemaVersion === 1) {
    return doc.name  // стара схема
  }
  return `${doc.firstName} ${doc.lastName}`  // нова схема
}
```

Міграція — **ліниво**: оновлюй схему документа при наступному запису, або запусти background job для поступової міграції старих документів.
