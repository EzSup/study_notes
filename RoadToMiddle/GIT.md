# Merge, Rebase, Cherry-pick

## Merge

Об'єднує дві гілки, створюючи **новий "merge commit"**, який містить зміни обох гілок.

Коли юзати:

- Коли хочеш **об'єднати код із двох гілок, не змінюючи історію**.
- Це **безпечний** спосіб інтеграції змін.
- Коли гілка **спільна** (кілька людей працюють на ній).

До:

```
   A---B---C (main)
        \  
         D---E (feature-branch)
```

Після:

```
   A---B---C---M (main)
        \      /
         D---E (feature-branch)
```

### Merge стратегії

**Fast-forward** — якщо `main` не рухався поки ти писав фічу, git просто пересуває вказівник вперед. Merge-коміту немає, історія лінійна. Відбувається автоматично коли можливо.

```bash
git merge feature-branch           # зробить fast-forward якщо можна
git merge --no-ff feature-branch   # примусово створити merge-коміт
```

**Squash merge** — всі коміти з гілки склеюються в один перед злиттям. PR з 15 "wip" комітами потрапляє в `main` як один охайний коміт. GitHub/Azure DevOps роблять це кнопкою "Squash and merge".

```bash
git merge --squash feature-branch
git commit -m "feat: add payment processing"
```

## Rebase

Переносить коміти з однієї гілки на іншу **без створення merge-коміту**, змінюючи їхню базу.

Коли юзати:

- Щоб **очистити історію** перед злиттям у `main` (не створюючи зайвих merge-комітів).
- Якщо хочеш **уникнути "розгалужень" в історії** (`git log` буде чистішим).
- Щоб підтягнути свіжі зміни з `main` у свою гілку.
- **Тільки на власних локальних гілках** — не роби rebase на спільних гілках.

До:

```
   A---B---C (main)
        \  
         D---E (feature-branch)
```

Після:

```
   A---B---C (main)
           \
            D'---E' (feature-branch)  
```

> **Важливо:** D' і E' мають ті самі зміни що D і E, але нові хеші — бо змінився батьківський коміт. Якщо зробиш `git push --force` після rebase на спільній гілці — у колег зламається локальна копія.

При rebase конфлікти можуть виникати **по одному на кожен коміт** — git переносить їх по черзі:

```bash
git rebase main

# конфлікт на D
git add src/Service.cs
git rebase --continue

# конфлікт на E
git add src/Other.cs
git rebase --continue

# або скасувати все:
git rebase --abort
```

### Interactive rebase

`git rebase -i` дозволяє переробити власну історію перед PR: склеїти коміти, перейменувати повідомлення, викинути зайве.

```bash
git rebase -i HEAD~3   # відкрити останні 3 коміти в редакторі
# pick   → залишити коміт
# squash → злити з попереднім
# reword → змінити повідомлення
# drop   → видалити коміт
```

## Cherry-pick

Копіює конкретний коміт з однієї гілки в іншу **без зміни всієї історії**.

Коли використовувати:

- Якщо треба взяти **тільки один коміт** з іншої гілки без злиття всіх змін.
- Класичний сценарій: баг знайдено на проді, фікс є в `develop` — беремо тільки його, не тягнучи незакінчені фічі.

До:

```
   A---B---C (main)
        \  
         D---E (feature-branch)
```

Після:

```
   A---B---C---E' (main)
        \  
         D---E (feature-branch)
```

```bash
git log --oneline feature    # знайти хеш потрібного коміту
git checkout main
git cherry-pick a1b2c3d      # застосувати його на main
```

Конфлікти можливі — вирішуються так само як при rebase:

```bash
git add src/PaymentService.cs
git cherry-pick --continue
# або скасувати:
git cherry-pick --abort
```

# Робота з історією та скасування змін

## 1. Ролбек локальних змін (до коміту)

Повертає файли до стану останнього коміту, видаляючи все, що ти написав, але ще не закомітив.

Коли юзати:

- Коли ти наговівся і хочеш почати з чистого листа.

```bash
git checkout -- .   # старий варіант
git restore .       # сучасний варіант
```

---

## 2. Відміна локального коміту

Скасовує останній коміт, який ти зробив, але ще не відправив (push) в origin.

### Зі збереженням змін (Soft)

Коміт зникає, але всі твої напрацювання залишаються у "Staging area" (готові до нового коміту).

Коли юзати:

- Забув додати файл або зробив помилку в тексті повідомлення.

```bash
git reset --soft HEAD~1
```

### Без збереження змін (Hard)

Коміт і всі зміни в ньому видаляються безповоротно.

Коли юзати:

- Якщо коміт був повністю помилковим і код у ньому не потрібен.

```bash
git reset --hard HEAD~1
```

---

## 3. Видалити коміт в Origin

Видаляє коміт з історії на сервері. **Увага:** Це змінює історію, що може створити проблеми колегам.

Коли юзати:

- Коли ти випадково запушив секретні дані (паролі) або абсолютно непотрібне сміття.

```bash
git reset --hard HEAD~1                    # локально
git push origin <branch-name> --force      # силове оновлення сервера
```

---

## 4. Ролбек коміту в Origin (Safe Revert)

Створює **новий коміт**, який робить зміни, протилежні вказаному коміту.

Коли юзати:

- Це **найбезпечніший** спосіб на публічних гілках. Історія не видаляється, а просто "відкочується" вперед.

```bash
git revert <commit-hash>
git push origin <branch-name>
```

До: `A---B---C`  
Після: `A---B---C---D` (де D — це анти-C)

---

## 5. Ребейзнути origin на певний коміт

Примусове встановлення гілки в origin на конкретний стан.

Коли юзати:

- Коли треба "відкотити" сервер на кілька кроків назад до стабільної версії.

```bash
git reset --hard <commit-hash>
git push origin <branch-name> --force
```

---

## 6. Список комітів у вигляді дерева

Дозволяє візуально зрозуміти, як розгалужувались і зливались гілки.

Коли юзати:

- Завжди, коли хочеш зрозуміти структуру проєкту перед merge або rebase.

```bash
git log --graph --oneline --all
```

> **Порада від Pragmatic Programmer:** Додай аліас для красивого дерева у свій `$PROFILE`, який ми щойно налаштували:
> 
> ```powershell
> Set-Alias gl "git log --graph --oneline --all --decorate"
> ```
> 
> Тепер просто ввівши `gl`, ти побачиш всю карту проєкту.

# Додаткові інструменти

## git stash

Відкладає незакомічені зміни "в стек", щоб переключитись на іншу задачу з чистим робочим деревом.

```bash
git stash                   # відкласти зміни
git stash pop               # повернути останні відкладені зміни
git stash list              # переглянути всі stash-и
git stash pop stash@{2}     # повернути конкретний
git stash drop stash@{0}    # видалити без застосування
```

---

## git reflog

Журнал всього що відбувалось з HEAD локально. Навіть якщо зробив `git reset --hard` і "втратив" коміти — вони ще живі. Reflog їх пам'ятає (зазвичай 90 днів). Тільки локально — на сервері reflog немає.

```bash
git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~2
# f4e5d6c HEAD@{1}: commit: fix payment bug   ← ось він

git checkout f4e5d6c        # або
git reset --hard f4e5d6c    # повернутись до втраченого коміту
```

---

## git blame

Показує хто і в якому коміті написав кожен рядок файлу.

```bash
git blame src/PaymentService.cs
# a1b2c3d (ihor   2024-03-15) public void Process() {
# f4e5d6c (anders 2024-02-01)   if (amount == null)
```

В Rider і VS Code це вбудовано — клікаєш на рядок і бачиш. В терміналі рідко потрібен, але корисно знати що це те саме під капотом.

---

## git tag

Мітка на конкретний коміт. Зазвичай для релізів.

```bash
git tag v1.2.0                          # lightweight — просто вказівник
git tag -a v1.2.0 -m "Release 1.2.0"   # annotated — з метаданими (стандарт для релізів)
git push origin v1.2.0                  # теги не пушаться автоматично з кодом
git push origin --tags                  # запушити всі теги
```

Annotated — стандарт для релізів (зберігає дату, автора, повідомлення). Lightweight — для особистих локальних міток типу "тут воно ще працювало".

---

## git bisect

Бінарний пошук по комітах — знаходить коміт в якому з'явився баг за O(log n) кроків замість ручного перебору. На репо з сотнями комітів знаходить винуватця за 7–8 кроків.

```bash
git bisect start
git bisect bad                # поточний стан — баг є
git bisect good v1.1.0        # тут ще все працювало

# git чекаутить середній коміт, ти тестуєш і кажеш:
git bisect good   # або
git bisect bad

# після кількох ітерацій git видає:
# a1b2c3d is the first bad commit

git bisect reset              # повернутись до поточного стану
```

## git hooks

Скрипти які git запускає автоматично при певних подіях. Живуть в `.git/hooks/` (не потрапляють в репо).

**pre-commit** — перед кожним комітом. Зручно для лінтера або форматера:

```bash
# .git/hooks/pre-commit
#!/bin/sh
dotnet format --verify-no-changes
```

**commit-msg** — перевірка формату повідомлення:

```bash
# .git/hooks/commit-msg
#!/bin/sh
if ! grep -qE "^(feat|fix|chore|refactor):" "$1"; then
  echo "Commit message must start with feat:|fix:|chore:|refactor:"
  exit 1
fi
```

**pre-push** — перед пушем, можна запускати тести.

> Оскільки `.git/hooks/` не потрапляє в репо, шерити хуки з командою незручно. Вирішується або скриптом що копіює хуки при клонуванні, або інструментами типу Husky (для JS-проєктів).

## fetch vs pull

```bash
git fetch origin    # завантажує зміни з сервера, але не застосовує їх
git pull            # fetch + merge в одну команду
```

`fetch` безпечніший — можеш подивитись що прийшло (`git log origin/main`) перед тим як злити. `pull` зручніший, але одразу змінює твою гілку.
